# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Voice Biomarker POC — a Next.js frontend (App Router, TypeScript) that records or accepts audio, POSTs it to an existing FastAPI backend, and renders acoustic depression/anxiety biomarker scores alongside a speech transcript and AI interpretation. The backend is fully built and running. The frontend app lives in `kintsugi-ui/` and its core flow is built:

- `app/components/VoiceBiomarker.tsx` — record/upload → replay → submit → loading state (state machine: idle/recording/recorded/loading/results/error). The idle screen shows a prototype disclaimer: not HIPAA-compliant, do not use real patient data.
- `app/components/ResultsView.tsx` — renders the disclaimer banner, both biomarker cards, AI interpretation sections, transcript, and a "Kintsugi raw output" section (numeric `raw_score` + `class` for both biomarkers, below the transcript)
- `app/components/DepressionCard.tsx`, `AnxietyCard.tsx` — separate components per the asymmetric scales below
- `app/lib/types.ts` — `AnalyzeResponse` / `BiomarkerScore` / `Interpretation` types matching the backend contract

`backend/` at the repo root is a local mirror of the FastAPI backend (`app.py`, `README.md`, `requirements.txt`, `vbp.service`) for editing convenience — it is **not** auto-deployed. Changes must be copied to `/home/ubuntu/voice-biomarker-poc/dam/app.py` on the EC2 box and the `vbp` service restarted; see Backend infra below.

Backend URL is read from `NEXT_PUBLIC_API_URL`. Local dev uses `kintsugi-ui/.env.local` (plain HTTP box IP). The production static build uses `kintsugi-ui/.env.production.local` (HTTPS CloudFront URL) — see Deployment below for why the filename matters.

## Commands

Run from `kintsugi-ui/`:

```bash
npm run dev       # start dev server (localhost:3000 — must use localhost, not an IP, for mic access over HTTP)
npm run build     # static export build (next.config.ts has output: "export") — produces kintsugi-ui/out/
npm run lint      # ESLint
```

`next build` picks up `.env.local` and `.env.production.local` automatically; there is no separate deploy script — see Deployment for the zip/upload steps. No test suite is configured.

**Next.js 16 caveat**: this project is on Next.js 16.3.3, newer than the training data for most models. `kintsugi-ui/AGENTS.md` (auto-regenerated by `next dev`, safe to keep committed) warns that APIs/conventions/file structure may differ from what you'd expect — check `kintsugi-ui/node_modules/next/dist/docs/` before relying on prior Next.js knowledge, especially for anything beyond the App Router basics already used here.

## Backend API contract

Base URL (direct, HTTP): `http://<ec2-public-ip>:8000`
Base URL (HTTPS, via CloudFront): `https://<distribution-domain>.cloudfront.net`

**GET /health** → `{"status": "ok", "model_loaded": true}`

**POST /analyze** — `multipart/form-data`, field `file` (audio blob, WebM from MediaRecorder is fine; backend normalizes via ffmpeg). Returns:

```json
{
  "depression":     { "raw_score": -0.9941, "class": 0, "label": "None (PHQ-9 <= 9)" },
  "anxiety":        { "raw_score": -0.8178, "class": 0, "label": "None (GAD-7 <= 4)" },
  "transcript":     "...",
  "interpretation": {
    "summary": "...", "depression": "...", "anxiety": "...",
    "transcript_observations": "...", "agreement": "...",
    "divergence": "...", "limitations": "..."
  },
  "processing_seconds": 19.04
}
```

Kintsugi's model (`KintsugiHealth/dam` on Hugging Face) only ever returns `{'depression': score, 'anxiety': score}` — no confidence values, embeddings, or per-segment data are documented or available. `raw_score`/`class` for both biomarkers is the complete Kintsugi output; nothing is being discarded server-side.

## Class scales — ASYMMETRIC, do not share one component

Depression (PHQ-9), **3 bands**: 0 = None (≤9), 1 = Mild-to-moderate (10-14), 2 = Severe (15+)

Anxiety (GAD-7), **4 bands**: 0 = None (≤4), 1 = Mild (5-9), 2 = Moderate (10-14), 3 = Severe (15+)

Each biomarker card must show both the class label and the raw score. Depression and anxiety cards must be implemented separately.

## Conceptual model (use in UI copy)

- **Kintsugi** = HOW they sound (acoustic only, never sees transcript)
- **Transcribe** = WHAT they said (semantic only)
- **Bedrock** = what the two may mean together (notes where they agree and diverge, stays in "screening signal, not diagnosis" framing)

Results must prominently state they are experimental and NOT a medical diagnosis. The idle/pre-recording screen must also state this is a non-HIPAA-compliant prototype and not to use real patient data — added because the demo previously had no warning before someone could submit real audio.

## Recording requirements

- Minimum 30 s, maximum 180 s (Kintsugi needs 30 s+ to be meaningful)
- MediaRecorder API for browser mic recording
- File upload from disk as an alternative input
- User must be able to replay before submitting

## Critical gotchas

1. ~~**CORS**~~ — fixed. Backend sends `access-control-allow-origin: *` (verified via `OPTIONS /analyze`). No action needed.

2. **Mic + HTTPS** — browser mic access requires HTTPS on all origins except `localhost`. Local dev on `localhost:3000` over HTTP works fine. The deployed frontend (Amplify) is HTTPS by default, satisfying this.

3. **Mixed content** — an HTTPS page cannot call a plain-HTTP backend. Solved for the deployed build by putting the backend behind its own CloudFront distribution (HTTPS in, HTTP to origin) — see Deployment.

4. **Non-elastic IP** — `<ec2-public-ip>` changes if the EC2 instance stops/starts. **Not yet fixed** — the backend CloudFront distribution's origin currently points at this IP (via the `sslip.io` DNS trick below), so a stop/start of the instance will break the CloudFront origin until it's updated or an Elastic IP is attached. Attach an EIP and update the distribution's origin `DomainName` before relying on this for a real demo.

5. **Security group** — port 8000 on `<sg-app>` is restricted to a single laptop IP (`<your-ip>/32`), kept for direct debugging. A second security group, `<sg-cloudfront-origin>` (name `vbp-cloudfront-origin`), is also attached to the instance and allows port 8000 from the AWS-managed CloudFront prefix list (`com.amazonaws.global.cloudfront.origin-facing`, id `pl-3b927c52`) — this is what lets the CloudFront distribution reach the origin. Both security groups are attached simultaneously (EC2 unions multiple SGs); do not remove either without checking what still needs it. Note this rule alone doesn't prove a request came through *your* distribution specifically — see the origin-secret header under Deployment, which closes that gap.

6. **CloudFront custom origins reject raw IPs** — `CreateDistribution` fails with `InvalidArgument: The parameter origin name cannot be an IP address` if the origin `DomainName` is a bare IP. Worked around with `sslip.io`, a free wildcard-DNS service that resolves `<ip-with-dashes>.sslip.io` to that IP with zero setup (no account, no Route 53): the backend distribution's origin is `<ip-with-dashes>.sslip.io`, which resolves to `<ec2-public-ip>`. If the EC2 IP changes, this hostname must be updated to match (see gotcha 4).

7. **Security group rule quota vs. the CloudFront managed prefix list** — adding `com.amazonaws.global.cloudfront.origin-facing` directly to `<sg-app>` failed with `RulesPerSecurityGroupLimitExceeded` (the prefix list alone counts as ~55 of the default 60-rule-per-SG quota). Fixed by creating a dedicated second security group for just that one rule (see gotcha 5) instead of requesting a quota increase — avoids touching the original SG's rules entirely.

8. **Next.js env file precedence** — `.env.local` outranks `.env.production` (load order is `.env.production.local` > `.env.local` > `.env.production` > `.env`). A production build with only a `.env.production` file will silently keep using whatever `.env.local` defines. Caught this the hard way: the first production zip still called the plain-HTTP box IP instead of the CloudFront URL, verified by grepping the built JS in `out/_next/static/chunks/` for the `fetch(...)` call. Fix: the production backend URL must live in **`.env.production.local`**, not `.env.production`.

9. **`localhost` vs `127.0.0.1` on the box** — `curl http://localhost:8000/...` from the EC2 box itself fails to connect (curl exit `000`), because `localhost` resolves to `::1` (IPv6) first and uvicorn (`--host 0.0.0.0`) only binds the IPv4 wildcard. Use `127.0.0.1` explicitly for any on-box testing.

10. **Processing time** — a full `/analyze` round-trip takes ~15-20 s (Transcribe is the slow leg). Show a meaningful loading/progress state.

## S3 audio file lifecycle

`run_transcribe()` in `backend/app.py` uploads the normalized WAV to S3 (`voice-biomarker-poc-<account-id>/audio/{uuid}.wav`) because Amazon Transcribe requires its source media to be in S3. This upload previously had no cleanup — every analyzed recording was left in the bucket permanently.

Fixed: the upload is now wrapped in `try/finally`, and the `finally` block best-effort-deletes the S3 object once Transcribe is done with it (success, failure, or timeout):

```python
finally:
    try: s3.delete_object(Bucket=BUCKET, Key=key)
    except Exception as e: print(f"warning: failed to delete s3://{BUCKET}/{key}: {e}")
```

The delete is wrapped in its own `try/except` deliberately — an earlier version let a delete failure raise out of `run_transcribe`, which killed the entire `/analyze` request with a 500 (visible in the browser as a misleading CORS error, since Starlette doesn't attach CORS headers to an unhandled-exception response). Root-caused via `journalctl -u vbp` on the box, which showed `botocore.errorfactory.AccessDenied ... s3:DeleteObject`: the EC2 instance's IAM role, `voice-biomarker-poc`, had S3 read/write but not delete. Fixed by attaching an inline policy:

```bash
aws iam put-role-policy \
  --role-name voice-biomarker-poc \
  --policy-name VoiceBiomarkerS3Delete \
  --policy-document '{
    "Version": "2012-10-17",
    "Statement": [
      { "Effect": "Allow", "Action": "s3:DeleteObject", "Resource": "arn:aws:s3:::voice-biomarker-poc-<account-id>/audio/*" }
    ]
  }'
```

Confirmed working (no more `AccessDenied` in the logs, objects no longer accumulate). Existing recordings uploaded *before* this fix are still sitting in the bucket — clean up manually if needed (`aws s3 rm s3://voice-biomarker-poc-<account-id>/audio/ --recursive`), no automatic backfill was run.

## Architecture decision — resolved: split, deployed

Went with **split**: Next.js hosted independently (AWS Amplify), backend stays on the EC2 box, fronted by its own CloudFront distribution for HTTPS. No custom domain, no ACM certificate, no nginx/certbot on the box. The base networking setup required no `app.py` changes; a follow-up access-control layer (below) did add a small one.

### Backend: CloudFront in front of EC2

- Distribution ID `<distribution-id>`, domain `<distribution-domain>.cloudfront.net`
- Origin: `<ip-with-dashes>.sslip.io:8000`, `OriginProtocolPolicy: http-only` (see gotcha 6 for why not the raw IP)
- Viewer protocol policy: redirect-to-HTTPS
- Cache policy: **CachingDisabled** (managed, `4135ea2d-6df8-44a3-9df3-4b5a84be39ad`) — responses are per-request and must never be cached
- Origin request policy: **AllViewer** (managed, `216adef6-5c7f-47e4-b989-5492eafa07d3`) — forwards all headers/query strings through
- Allowed methods: GET, HEAD, OPTIONS, PUT, POST, PATCH, DELETE (POST required for `/analyze`)
- Config was written with `printf` to a JSON file rather than a bash heredoc or a long single-line `jq` command — CloudShell repeatedly mangled both (heredocs hung on a mismatched closing delimiter; a long one-line `jq '...'` got line-wrapped mid-paste into two commands). The `printf '%s' '<content>' > file` pattern was the one that reliably survived copy-paste into CloudShell for anything long or multi-line.

### Backend access control: origin-secret header (closes the "anyone can point their own CloudFront at your IP" gap)

The security group only proves a request came from *some* CloudFront distribution's IP range, not specifically this one's — anyone who learns the raw IP could stand up their own CloudFront distribution pointed at it and reach the backend directly, bypassing this distribution entirely. Closed with the AWS-standard fix for custom HTTP origins: an origin custom header that CloudFront injects on every request it forwards, checked by the app itself.

- CloudFront origin config carries `OriginCustomHeaders: [{ HeaderName: "X-Origin-Verify", HeaderValue: <secret> }]`, added via `update-distribution` (the header value is only in the distribution config and the box's `.env` — never in this repo).
- `backend/app.py` checks it via a FastAPI dependency, applied to both `/health` and `/analyze`:
  ```python
  ORIGIN_SECRET = os.environ["ORIGIN_SECRET"]  # fails loudly if unset — do NOT default to ""

  def verify_origin(x_origin_verify: str = Header(default="")):
      if x_origin_verify != ORIGIN_SECRET: raise HTTPException(403, "Forbidden")
  ```
  `os.environ["ORIGIN_SECRET"]` (not `.get()`) is deliberate: it crashes the app on startup if the secret isn't configured, rather than silently defaulting to `""` — which would make `"" == ""` pass and defeat the check entirely for anyone sending no header at all.
- The secret itself lives **only** in `/home/ubuntu/voice-biomarker-poc/dam/.env` on the box (`ORIGIN_SECRET=...`), created directly there via SSH, never copied from this machine. `backend/vbp.service` loads it via `EnvironmentFile=/home/ubuntu/voice-biomarker-poc/dam/.env`. `backend/.gitignore` excludes `.env`, `.venv/`, and bytecode in case this folder is ever put under git.
- `VBP_BUCKET` lives in the same `.env` and is read the same way (`os.environ["VBP_BUCKET"]`, no default, fails loudly). An S3 bucket name has to be globally unique, so the convention here suffixes it with the account id, which makes the bucket name itself an account identifier and not something to hardcode in a source file.
- **No frontend changes needed** — the header is injected between CloudFront and the origin, never touching the browser leg, so the deployed frontend works unmodified.
- Confirmed working directly on the box (bypasses the security group, tests the app logic in isolation): `curl http://127.0.0.1:8000/health` → `403`; same request with `-H "X-Origin-Verify: <secret>"` → `200`. (Note: `curl http://localhost:8000/...` resolves to `::1` on this box and fails to connect at all, since uvicorn only binds the IPv4 wildcard — use `127.0.0.1` explicitly for on-box testing.)
- Residual gap: this stops anyone without the secret, full stop — including legitimate direct testing. Any future script/tool that needs to call the backend directly (bypassing the frontend) must send this header.

### Frontend access control: Amplify Basic Auth

The origin-secret header stops the backend being called *directly*, but did nothing to stop anyone with the Amplify URL from just using the site itself — each recording (up to 3 min) costs real Transcribe + Bedrock spend, and nothing rate-limits repeated use. Closed with Amplify Hosting's built-in Basic Auth, enabled per-branch (no code change, no CloudFront/distribution change):

```bash
aws amplify update-branch \
  --app-id <amplify-app-id> \
  --branch-name production \
  --enable-basic-auth \
  --basic-auth-credentials "<base64 of user:password>"
```

- App id `<amplify-app-id>`, branch `production` (from the live URL `https://production.<amplify-app-id>.amplifyapp.com/`)
- Credential value is intentionally **not** recorded here, same reasoning as `ORIGIN_SECRET` — the user set it directly, known to them, not written into any file that could end up in a repo. Rotate via the same `update-branch` command with a new base64 value if needed; disable with `--no-enable-basic-auth`.
- AWS confirms this throttles repeated failed login attempts automatically (built-in brute-force protection, not something set up manually).
- Enabled and confirmed live — a browser hitting the Amplify URL now gets an HTTP Basic Auth prompt before the page loads.

### Full protection stack, end to end

1. Browser → Amplify: HTTP Basic Auth gate (this section)
2. Browser → CloudFront (frontend): HTTPS only, static files
3. Frontend JS → CloudFront (backend): HTTPS, CORS `*`
4. CloudFront (backend) → EC2: security group restricts to CloudFront's IP range + one laptop IP, **and** the origin-secret header (previous section) rejects anything that arrives without it — closes the gap where someone else's CloudFront pointed at the raw IP would otherwise get through the security group alone

**Outstanding for this piece:** the origin still points at the box's non-elastic IP (gotcha 4) — attach an Elastic IP and update the origin's `DomainName` (and the `sslip.io` hostname to match) before treating this as durable.

### Frontend: AWS Amplify Hosting, manual zip deploy (no GitHub)

`kintsugi-ui` has no git remote configured, and a GitHub connection was explicitly ruled out, so this uses Amplify's manual deploy path instead of git-connected CI/CD:

1. `next.config.ts` sets `output: "export"` — the app has no API routes and no server-only data fetching (`page.tsx` renders a single client component), so it's fully static-exportable; confirmed via a clean `npm run build`.
2. `kintsugi-ui/.env.production.local` sets `NEXT_PUBLIC_API_URL=https://<distribution-domain>.cloudfront.net` (see gotcha 8 for why it can't be `.env.production`).
3. Build (`npm run build`) generates `kintsugi-ui/out/`; zip its **contents**, not the folder itself (Amplify's docs warn zipping the wrapping folder causes an Access Denied error) — done as `kintsugi-ui/kintsugi-ui-build.zip`.
4. Deploy via Amplify console → **Create new app** → **Deploy without Git** → App name `kintsugi-ui`, Branch `production`, Method **Drag and drop** → upload the zip.

Redeploying after any frontend change: rebuild, re-zip, re-upload through the same console flow (or the `aws amplify create-deployment` / `start-deployment` CLI flow, if scripting it later).
